SENTINELDRIVE - FORMATO JSON MQTT ACEPTADO
Fecha: 2026-05-19

OBJETIVO
La aplicacion NO distingue si la velocidad viene de GPS, OBD, IA u otra fuente.
La aplicacion solo necesita el valor canonico de velocidad bajo la clave:

  speed

Durante la transicion, el backend sigue aceptando aliases legacy:

  speed_gps
  speed_obd

Pero el formato recomendado y oficial desde ahora es usar solo:

  speed


TOPICS MQTT
1. Ubicaciones GPS:
   flota/ecuador/buses/<bus_id>/gps

2. Eventos:
   flota/ecuador/buses/<bus_id>/event


REGLAS GENERALES
1. Todo payload debe ser JSON valido.
2. bus_id es obligatorio y debe ser un entero mayor a 0.
3. timestamp es obligatorio y debe ser ISO 8601 valido.
   Ejemplos:
   - 2026-05-19T10:15:30
   - 2026-05-19T10:15:30Z
   - 2026-05-19T10:15:30-05:00
4. lat y lon deben existir cuando el mensaje representa ubicacion o evento georreferenciado.
5. speed es la clave oficial para velocidad.
6. El backend guarda la velocidad como un numero simple, sin importar su origen.
7. Si llega un alias legacy (speed_gps o speed_obd), el backend lo acepta por compatibilidad.


FORMATO ACEPTADO PARA GPS
Payload minimo recomendado:

{
  "bus_id": 1,
  "type": "gps",
  "timestamp": "2026-05-19T10:15:30Z",
  "lat": -4.012345,
  "lon": -79.201234,
  "speed": 46.7
}

Campos usados por la aplicacion:
- bus_id: obligatorio
- timestamp: obligatorio
- lat: obligatorio
- lon: obligatorio
- speed: recomendado

Compatibilidad temporal tambien aceptada:

{
  "bus_id": 1,
  "type": "gps",
  "timestamp": "2026-05-19T10:15:30Z",
  "lat": -4.012345,
  "lon": -79.201234,
  "speed_gps": 46.7
}

o

{
  "bus_id": 1,
  "type": "gps",
  "timestamp": "2026-05-19T10:15:30Z",
  "lat": -4.012345,
  "lon": -79.201234,
  "speed_obd": 46.7
}

Si llegan varias claves de velocidad a la vez, la prioridad actual del backend es:
1. speed
2. speed_obd
3. speed_gps


FORMATO ACEPTADO PARA EVENTOS
Payload base:

{
  "bus_id": 1,
  "type": "event",
  "event": "exceso_velocidad",
  "timestamp": "2026-05-19T10:16:00Z",
  "lat": -4.012345,
  "lon": -79.201234
}

Clave event aceptada:
- exceso_velocidad
- frenado_brusco
- curva_peligrosa
- conduccion_agresiva
- sobrecalentamiento
- otros
- otro


EVENTO: exceso_velocidad
Formato recomendado:

{
  "bus_id": 1,
  "type": "event",
  "event": "exceso_velocidad",
  "timestamp": "2026-05-19T10:16:00Z",
  "lat": -4.012345,
  "lon": -79.201234,
  "speed": 93.4
}

Compatibilidad temporal:
- speed_obd
- speed_gps

La aplicacion usa ese valor como "value" del evento.

EVENTO: otros / otro

{
  "bus_id": 1,
  "type": "event",
  "event": "otros",
  "timestamp": "2026-05-19T10:16:00Z",
  "lat": -4.012345,
  "lon": -79.201234,
  "description": "Presion de llantas (psi)",
  "value": 28.5
}

Reglas especiales:
- description es recomendada para identificar el sensor
- value puede ser numero o string numerico
- si value no puede convertirse a numero, el valor del evento queda vacio


QUE JSON SI ACEPTA
1. JSON bien formado.
2. bus_id valido.
3. timestamp ISO valido.
4. lat/lon numericos cuando corresponde.
5. speed como nombre oficial para velocidad.
6. Aliases legacy speed_gps y speed_obd por compatibilidad temporal.
7. temperature o temp para sobrecalentamiento.


QUE JSON NO ACEPTA
1. JSON mal formado.
2. bus_id ausente, cero o negativo.
3. timestamp ausente o invalido.
4. lat o lon no numericos en mensajes GPS.
5. event con nombre no reconocido.
6. bus_id que no exista en la base de datos.


EJEMPLOS DE JSON INVALIDO
1. Sin bus_id:
{
  "type": "gps",
  "timestamp": "2026-05-19T10:15:30Z",
  "lat": -4.0,
  "lon": -79.2,
  "speed": 40
}

2. Sin timestamp:
{
  "bus_id": 1,
  "type": "gps",
  "lat": -4.0,
  "lon": -79.2,
  "speed": 40
}

3. Evento no reconocido:
{
  "bus_id": 1,
  "type": "event",
  "event": "speed_gps",
  "timestamp": "2026-05-19T10:16:00Z"
}

4. GPS sin coordenadas validas:
{
  "bus_id": 1,
  "type": "gps",
  "timestamp": "2026-05-19T10:15:30Z",
  "lat": "abc",
  "lon": -79.2,
  "speed": 40
}


LOGICA INTERNA RESUMIDA
1. El topic /gps crea un registro de ubicacion.
2. El topic /event crea un registro de evento.
3. Para velocidad, la app toma primero speed.
4. Si no existe speed, intenta speed_obd.
5. Si tampoco existe, intenta speed_gps.
6. La fuente real de la velocidad no se guarda en la app.
7. La logica de origen del dato debe resolverse en el hardware del vehiculo.


RECOMENDACION FINAL PARA EL HARDWARE
Desde ahora, enviar asi:
- GPS con speed
- evento exceso_velocidad con speed

Evitar enviar en nuevos dispositivos:
- speed_gps
- speed_obd

Esos nombres quedan solo como compatibilidad temporal.
